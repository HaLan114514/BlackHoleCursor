## 问题 1：帧率过低（原问题 2）

> ✅ **第 12 步已定位并修复**（见文末「执行记录 · 第 12 步」）：真凶是**系统定时器粒度**，不是抓屏、不是预览。
> 32.1 FPS → **57.0 FPS**，PRD 要求的「1080p 下 ≥55 FPS」达成。

**定位结论：已定位（埋点数据说话）。** 32.1 FPS ≈ 1/31.2ms —— 正好是 Windows 默认 15.6ms 定时器粒度的两倍；
渲染线程 `WaitAndPump(1)` 名义上等 1ms，实际睡满一两个时钟滴答。
在覆盖层线程调用 `timeBeginPeriod(1)` 后立刻回到 57 FPS。

**实测数据（埋点后，真实 GPU，你的「我的预设2」参数，窗口 362×362）**

| 场景 | 平均 FPS | 抓屏 | 渲染 | Present | 整帧 |
|---|---|---|---|---|---|
| 修复前 · 静止（预览开） | **32.1** | 0.12 ms | 0.10 ms | 0.14 ms | 0.75 ms |
| 修复前 · 移动 | **32.1** | 0.09 ms | 0.13 ms | 0.17 ms | 0.70 ms |
| 修复前 · 隐藏主界面（预览停） | **32.2** | 0.08 ms | 0.13 ms | 0.13 ms | 1.00 ms |
| **修复后 · 静止** | **57.0** | 0.07 ms | 0.10 ms | 0.13 ms | 0.53 ms |
| **修复后 · 移动** | **57.0** | 0.07 ms | 0.11 ms | 0.14 ms | 0.52 ms |

读法：三段 CPU 耗时加起来不到 0.4ms、整帧 0.7ms，却只有 32 FPS ——
说明时间全都花在 Tick **之外**（等待）上，于是把矛头指向线程的等待机制而不是抓屏/渲染。

**候选的处置（按实测结果）**

| # | 候选 | 结论 |
|---|---|---|
| a | 抓屏链路 | **排除**：抓屏段只有 0.06~0.12 ms，且抓屏降级=False（走的是 DXGI 而非 GDI） |
| b | 主界面预览 | **排除**：隐藏主界面停掉预览后仍是 32.2 FPS，毫无变化 |
| **c** | **覆盖层线程忙等的等待粒度** | ✅ **命中**：`WaitAndPump(1)` 实际睡 ~31ms（15.6ms 粒度 × 2）。`timeBeginPeriod(1)` 后 → 57 FPS |
| d | 全黑帧检测回读 | 未观察到尖峰（抓屏段均值稳定在 0.1ms 以下），不需处理 |
| e | 分层窗口 | 未单独测（它是点击穿透的必要条件，红线不能动）；修完 c 后帧率已达标，不再折腾 |
| f/g | 窗口面积 | 未测：修完 c 后 362×362 已能跑满 57 FPS；若将来把透镜半径拖到最大，可回头看这一项 |

**计划里列为候选项、但按实测决定不做的**

- **抓屏降频**（桌面静止时复用上一帧）：抓屏只要 0.07ms，省它毫无意义，反而会让桌面变化时扭曲层滞后。不做。
- **预览与主渲染共用设备 / 预览降帧率**：预览对覆盖层帧率毫无影响（57.0 vs 57.0）。不做，
  只在「预览本身占一点 CPU」这个层面留作可选优化。

**已列出的候选瓶颈（按怀疑程度排序）**

| # | 候选 | 依据 |
|---|---|---|
| a | 抓屏链路 | 每帧 `AcquireNextFrame(0)` + `CopySubresourceRegion`；日志中曾出现 `Timeout` 与降级。若实际落到 GDI `BitBlt` 兜底，每帧一次 `CopyFromScreen` + `UpdateSubresource` 会非常慢 |
| b | 主界面预览 | `PreviewSurface` 用**另一套** D3D11 设备离屏渲染 184×184 并 `Marshal.Copy` 回读，30fps；且主界面打开时覆盖层被强制满帧 → 负载翻倍 |
| c | 覆盖层线程忙等 | `WaitAndPump(1)` 每秒唤醒约 1000 次 |
| d | 全黑帧检测回读 | 每 20 帧一次 `Map()`（GPU→CPU 同步），会造成**周期性掉帧**而非平均帧率低 |
| e | 分层窗口 | `WS_EX_LAYERED` 走 DWM 另一条合成路径，可能与 DComp 叠加出额外拷贝 |
| f | 窗口面积 | 透镜半径 180 → 窗口 360×360；最大可到 1024×1024，抓屏+渲染面积直接决定开销 |
| g | **第 2 步带来的窗口变大**（新增） | 修好光晕裁切后，窗口半径要额外容纳「光晕可达半径」：默认 360→371，而「我的预设2」参数下 **188→491（像素约 6.8 倍）**。埋点时要重点看这一项，必要时给光晕房间加绝对上限或质量档位 |

**计划做法**

1. 先把 `OverlayController.Tick()` 拆成三段计时并周期性写日志：
   `抓屏 / 渲染 / Present`，同时在 `SystemView` 显示分项耗时。
2. 用真实数据确认瓶颈后再动手，优先做这几项（按实测结果取舍）：
   - 抓屏降频：透镜背景不必每帧更新（桌面静止时直接复用上一帧纹理）
   - 覆盖层线程改为按目标帧率计算等待时长，不再 1ms 忙等
   - 预览与主渲染共用同一个 D3D11 设备，并降低预览帧率
   - 全黑帧检测改为异步回读或进一步降频
   - 评估分层窗口开销，必要时做成可开关并给出对比数据

## 问题 2：黑洞外面套着一个明显的大正方形，正方形消失时留下一个很丑的圈

**现象**：黑洞周围有一个清晰的正方形（随窗口尺寸变化）；某些情况下正方形不见了，但换成一个很难看的硬边圆环。

> **第 1 步（取证）已完成 —— 定位结论：已确认。**
> **大正方形 = 黑洞外层的「加色光晕」被覆盖层窗口矩形硬裁出来的亮边。**
>
> `blackhole.hlsl:61-63` 的光晕是 `result.rgb += ... * glow`（只加 rgb、不加 alpha），
> 衰减方式是 `exp(-(r-outerR)/(outerR*0.9))`，衰减很慢；而覆盖层窗口只有
> `2 × max(透镜半径, 视觉半径)` 见方（`OverlayController.cs:214-216`），**窗口半径从未考虑光晕可达范围**。
> 于是光晕在还没衰减完的地方被窗口矩形切断 → 桌面上显形为一个正方形亮边。

**三条证据**

| # | 证据 | 结论 |
|---|---|---|
| 1 | 日志 `log.txt:498`：`首帧渲染完成：窗口 188x188 @(1394,164)，交换链 FlipDiscard/Premultiplied` | alpha 模式正常 → **候选 a（AlphaMode.Ignore）排除**；窗口 188 = 视觉半径 93.6×2，而光晕衰减到 1% 需要 **245 px** → 窗口根本装不下 |
| 2 | 数学（新增 `GlowMath` 量化） | 你的「我的预设2」参数：窗口边界处加色光晕 **≈8%（≈20/255 亮度）** → 明显可见的直边；默认参数（环 36 / 窗口 360）边界光晕 **≈0.6%（≈1.5/255）** → 几乎看不见。**这正好解释「某些情况下正方形会消失」**——取决于环大小 / 缩放 / 透镜半径的比例 |
| 3 | 截图 `smoke6.png` | 光晕左、下两侧能看到被裁出的直线边界 |

**原 4 个候选的处置**

| # | 候选 | 现状 |
|---|---|---|
| a | 交换链退到 `AlphaMode.Ignore` | **已排除**（日志为 `FlipDiscard/Premultiplied`） |
| b | 合成绑定中间帧空窗 | 未证实，暂不作为主因；作为防御性改动保留 |
| c | 分层窗口整窗 alpha=255 | 不是成因（它是必要条件，不是充分条件），保留不动 |
| d | 背景覆盖圆 / 抓屏错位 | 未证实；正方形尺寸完全跟随窗口，符合光晕裁切解释，暂不处理 |

「很丑的圈」的两个来源（正方形消失时只剩黑洞本体，圈就暴露了）：

**"很丑的圈"已定案（你的回答）：就是可调的那个吸积盘本体**，不是光子环、也不是外层光晕。
所以改动目标锁定 `blackhole.hlsl:22-31` 的盘面着色——与 N2（碎石带）是同一段代码，两者必须一起做：

- `radial = smoothstep(0, 0.12, t) * (1 - smoothstep(0.70, 1.0, t))`：内外边不对称（内侧 12% 急亮、外侧 30% 缓灭），
  在默认细环（粗细 6）上会呈现"硬边 + 半透明带"；
- `turbulence`（0.72~1.0 的 value noise）与 `doppler`（0.70~1.30）都跟着同一个 `spinPhase` 转
  → 就是你说的"像一个固定的圈在转"（N2 会一并解决）；
- 默认参数本身也难看（发光 1.0 过曝、环半径 30 太细），这部分由问题 5 的骨架解决。

（次要：`blackhole.hlsl:60` 的光子环宽度仅 `horizon × 0.18`、`lens.hlsl:36` 的爱因斯坦环，
这两条仍按原计划软化，但不再是本次的主目标。）

**补充证据（你拍的照片，正方形修掉之后）**

照片里正方形确实没了，但黑洞外面有一圈**奶白色的圆环**套在吸积盘外面，
盘和环之间还有一圈暗缝，环外再拖一大片模糊光斑 —— 这就是「有时候还是会有一个圈」。

成因已定位（还是 `blackhole.hlsl` 的光晕，两个缺陷叠加）：

1. **驼峰**：`outsideDisk = smoothstep(0.85R, 1.15R, r)` 让光晕从盘缘往**外**爬坡，
   在 `1.15R` 处才到峰值（≈0.85），而此时吸积盘自身的亮度已经在 `t=1.0`（即 `R`）处衰减到 0
   （`radial` 的 `1 - smoothstep(0.70, 1.0, t)`）。
   结果：盘先暗下去 → 光晕再亮起来 → **暗缝 + 独立亮环**，观感上就是"套了一个圈"。
2. **拖尾太长**：衰减常数 `k = 0.9R`，光斑能拖到 `3~5R` 以外，形成一大片模糊光晕。
3. 「**有时候**」的原因：光晕是加色输出，**背景越暗越明显**——深色桌面上看得清，
   亮色窗口上就"消失"了，所以时有时无。

量化（你的参数，盘外半径 47.7）：光晕峰值在 `1.15 × 47.7 ≈ 55px` 处，
亮度 ≈ 0.85 × 0.55 × 0.42 ≈ **20%**（≈50/255 的奶黄色）→ 与照片里的白环吻合。

**验证方法（第 1 步已做完，结论见上）**

1. ~~确认 alpha 模式~~ → 已确认 `FlipDiscard/Premultiplied`，候选 a 排除。
2. ~~方块是否跟随窗口尺寸~~ → 是（188×188 与窗口一致），符合光晕裁切。
3. ~~关掉透镜复现~~ → 无需再做，「圈」的归属已由你确认（吸积盘本体）。

**修正后的计划做法（与问题 4 同源、一起做）**

1. ✅ **窗口半径纳入光晕可达半径**：`radius = max(透镜半径, 视觉半径, GlowMath.Reach(盘外半径))`，
   并受 `SettingsRanges.OverlayMaxExtent / 2`（512）上限约束 → 光晕永远装得下，正方形消失。（第 2 步已完成）
2. ✅ **halo 强制在窗口内归零**（双保险）：`halo *= 1 - smoothstep(reach*0.75, reach, r)`。（第 2 步已完成）
3. ✅ 光效与透镜参数解耦：光子环半径/宽度改由视界半径在着色器内推出，不再读 `LensParams`。
   （原方案"新增 GlowParams 常量"不需要了——由视界推算即可，不用扩容常量缓冲区。）（第 2 步已完成）
4. ✅ **光晕收形（针对照片里的白环）**：（第 3 步已完成）
   - 去掉 `outsideDisk` 造成的驼峰：光晕从盘缘（`R`）起峰、**单调向外衰减**，
     与吸积盘的亮度在盘缘处衔接，消灭「暗缝 + 独立亮环」；
   - 衰减常数 `k = 0.9R → 0.45R`，光斑收拢成贴盘的辉光，不再拖一大片；
   - 副产品：光晕可达半径 `5.145R → 3.07R`，覆盖层窗口跟着变小
     （你的参数 491×491 → 约 294×294），**帧率也受益**。
5. ⬜ 交换链一旦退到 `AlphaMode.Ignore`，主动降级为「只画黑洞本体」（防御性，候选 a 的兜底）。
6. ⬜ 顺序调整：`ResizeBuffers → BindComposition → SetVisible(true)`（防御性，候选 b）。
7. ⬜ **吸积盘本体重画**（与 N2 碎石带一起做）：内外边对称软化并随粗细自适应；

## 问题 4：引力透镜的「影响半径」会影响黑洞自身光效

**现象**：拖动「影响半径」时，黑洞自己的光环 / 光晕也跟着变。

**定位结论：已确认存在耦合，有两条路径。**

1. **着色器常量混用**：`blackhole.hlsl:60` 的光子环读的是 `LensParams.y`（语义是「光子环半径」）与 `Timing.z`（「光子环宽度」），而同一个 `LensParams` 的 `z/w`（渐隐内/外界）是由 `LensRadius` 算出来的（`SceneConstants.cs:90-94` → `LensMath.FadeInner/FadeOuter`）。黑洞本体的光效不该读透镜参数。
2. **窗口尺寸连带**（**已由第 1 步量化确认**）：窗口半径 = `max(EffectiveLensRadius, VisualRadius)`（`OverlayController.cs:214-216`），
   而 `blackhole.hlsl:61` 的光晕 `halo = exp(-(r-outerR)/(outerR*0.9))` 在窗口边缘未必衰减到 0
   → 改「影响半径」= 改窗口大小 = 改光晕被裁切的位置。

   实测两组参数（用新增的 `GlowMath` 算出）：

   | 参数 | 透镜半径 | 视觉半径 | 窗口半径 | 盘外半径 | 窗口边界光晕 |
   |---|---|---|---|---|---|
   | 默认 | 180 | 57.6 | **180** | 36 | ≈0.6%（≈1.5/255，不可见） |
   | 我的预设2 | 52.4 | 93.6 | **93.6** | 47.7 | **≈8%（≈20/255，明显可见）** |

   即：拖「影响半径」会同时改变窗口尺寸与光晕被裁切的位置 → 观感上就是「影响半径在改黑洞的光」。
   （这条同时是问题 2 的成因，两者第 2 步一起修。）

**计划做法**

1. 黑洞本体光效（光子环半径/宽度、光晕衰减）改为只由「视界半径 + 环半径 + 发光强度」决定，新增独立的 `GlowParams`，不再读 `LensParams`。
2. 光晕必须在窗口内衰减到 0：`halo *= 1 - smoothstep(reach*0.75, reach, r)`，杜绝窗口边界硬切。
3. 窗口半径改为 `max(EffectiveLensRadius, VisualRadius, 光晕可达半径)`，任何参数下都不裁光晕。
4. 单测（`SceneParamsBuilder`）：只改 `LensRadius` 时，除 `LensParams.z/w` 与 `Viewport` 外，其余常量一律不变。

## N3：吸积盘可以左右倾斜

**需求**：现在只能"前后俯仰"，希望盘还能左右歪。

**现状**：`blackhole.hlsl:17-20` 只有一次逆透视 `disk = float2(d.x, d.y / cosT)`，椭圆长轴被写死在水平方向；
`SceneParamsBuilder` 只传 `cosT / sinT`（`SceneConstants.cs:82`），没有任何"绕视线轴旋转"的分量。

**数学（已推导，直接可用）**

设盘面坐标 `(X, Y)`，先绕视线轴 roll（φ），再绕 x 轴 tilt（θ）投影到屏幕：

```
u =  X*cosφ - Y*sinφ
v =  X*sinφ + Y*cosφ
屏幕 = (u, v*cosθ)        深度 ∝ v*sinθ
```

着色器里要的是反解：

```
v = d.y / cosθ ;   u = d.x
X =  u*cosφ + v*sinφ
Y = -u*sinφ + v*cosφ
rho = length(X, Y) ;  ang = atan2(Y, X) + spinPhase
```

**关键结论：深度只与 `d.y` 有关**（roll 绕的是视线轴，不改变远近），
所以 `frontHalf = (d.y * tanT) >= 0`（`blackhole.hlsl:33`）**不用改**，前后半盘遮挡逻辑天然保持正确。

**计划做法**

1. 新增设置 `RingRoll`：范围 **-90 ~ 90°**（盘面 180° 对称，超出等价），默认 0，与 `RingTilt` 完全独立。
2. `blackhole.hlsl` 在逆透视前插入上面的 roll 反解；`turbulence` / `doppler` 的取角全部改用新的 `(X, Y)`。
3. 光子环与光晕是径向对称的，不受 roll 影响，无需改动。
4. UI：外观页新增「左右倾斜」滑块，与「倾斜角度」并排（后者改名「前后倾斜」以免歧义），预览实时同步。
5. 单测：`RingRoll` 变化只影响 roll 相关分量；`RingRoll = 0` 时渲染结果与改动前逐像素一致（回归保护）。

> **共享前置改动：着色器常量缓冲区扩容**
> `common.hlsl` 的 `SceneParams` 现在是 8 × float4 = 32 floats（`SceneConstants.FloatCount = 32`），**已经占满**。
> 但下面几项都要往里塞新参数：N3 的 roll、N2 的碎石数量、问题 4 的独立 `GlowParams`、N4 的淡入淡出进度。
> 方案：新增一个 `float4 Extra`（roll / debrisCount / glowReach / fade），`FloatCount` 32 → 36；
> `SceneConstants.ToFloatArray()` 与 `common.hlsl` 的 cbuffer 必须同步改，
> 并补一条「序列化数组长度 == FloatCount」的断言型单测，防止 C# 与 HLSL 两边脱节。
> 放在 N3 里一起做，因为它是最先需要新常量的。

**第一版实现错了（你反馈"只做了个标在那，实际上用不了"）**

我把 roll 施加在**未压扁**的圆盘坐标上：`disk = Rz(φ)·(d.x, d.y/cosT)`。
但**圆绕自身中心旋转还是同一个圆**，再压扁得到的椭圆完全不变 ——
视觉上盘根本没歪，只有盘面纹理（噪声/多普勒）在转，等于没效果。

**修正**：roll 必须旋转「**压扁之后**」的椭圆，也就是盘面长轴在屏幕里的朝向：

```
正演：屏幕 = Rz(φ) · (X, Y*cosθ)      深度 z = Y*sinθ
反演：X =  d.x*cosφ + d.y*sinφ ;  Y = (-d.x*sinφ + d.y*cosφ) / cosθ
```

同时深度也随之改变，`frontHalf` 改成 `(-d.x*sinφ + d.y*cosφ) * tanT >= 0`
（roll=0 时退化为原来的 `d.y*tanT >= 0`，行为不变）。
不改的话，被视界遮挡的半边会判断错。

**新增 5 条单测**

- `RingRoll_IsConvertedToRadiansInExtra`：90° → π/2，落在 `Extra.x`（索引 32）；
- `RingRoll_DoesNotAffectAnyOtherConstant`：改 roll 只动 `Extra.x`，其余 35 个常量全部不变；
- `RingRoll_IsClampedToLegalRange`：±999 被钳到 ±90；

## 已解决（已从待办移除）

- **单测污染用户的真实文件（第 10 步之后补做，✅ 已修复）**：
  `RuntimeLog.FilePath` 是写死的 `%LOCALAPPDATA%\BlackHoleCursor\log.txt`，
  单测会往里面灌假的「首帧渲染完成」「抓屏失败」，且用的是**默认参数**（盘外半径 36），
  与实机日志混在一起根本分不清真假（第 2 步、第 10 步各被误导一次）。
  排查期间还实测到用户的「我的预设2」与 `settings.json` 被写入了非用户的数值，已手工还原。
  修法：`RuntimeLog` 增加 `RedirectToDirectory()` / `UseDefaultPath()` / `IsWritingToUserProfile`，
  测试项目用 `[ModuleInitializer]` 在程序集加载时重定向到临时目录；
  另加 3 条防回归断言（其中一条真的写一行日志、再确认它没出现在用户 log.txt 里）。
  验证：跑完 284 条测试，三个用户文件哈希全部未变。
  顺带确认 `SettingsService` / `PresetService` 本来就支持传入目录，
  两个测试类用的都是临时目录 —— 这部分没有漏洞，不需要改。
- **光标没隐藏**：`ShowCursor(FALSE)` 实测无效（计数 -1 仍显示），改为 `SetSystemCursor`
  把 13 个标准系统光标替换为透明光标，退出用 `SPI_SETCURSORS` 还原。
- **点击造成未响应**：覆盖层线程没有消息循环，已加 `WaitAndPump`
  （`MsgWaitForMultipleObjectsEx` + `PeekMessage`）。
- **点击被覆盖层吃掉**：`HTTRANSPARENT` 只在同一线程内有效，最终用
  `WS_EX_LAYERED | WS_EX_TRANSPARENT` + `SetLayeredWindowAttributes(0xFF)` 实现穿透。
- **问题 4（启用开关太小 / 调坏后难恢复）**：
  1. 指针进入主窗口或托盘菜单时恢复系统光标（60ms 轮询判定，`MouseLeave` 不可靠）；
  2. 「启用黑洞」换成 `BigSwitch` 大号开关（82×44 轨道 + 状态文字）；
  3. 全局快捷键 `Ctrl+Alt+B` 切换启用；
  4. 新增「撤销改动」按钮（`SettingsService` 撤销历史，连续改动按 700ms 合并，
     「恢复默认」也可撤销）。
- **顺带修复**：`PostMessage` / `SystemParametersInfo` 入口点错误
  （`user32` 只导出 A/W 版本），前者会让二次启动变成僵尸进程。
