## 问题 1：某种亮度背景下光效大幅减少甚至消失

**现象**（你的原话）
> 已知所有黑洞在开启后在不同亮度的背景下有不同的特效，但是有一种情况会导致光效大幅减少或者直接消失，特别难看。

**对照组的含义（由 `2.jpg` 正常 / `3.jpg` 消失 确立）**
两者同为 Quasar 预设，唯一差别是**桌面背景**：有内容/偏亮的背景 → 成片同心光环 + 亮带（2）；
暗背景 → 只剩盘本体和一圈细环（3）。所以变量是**「桌面上有没有东西可以折射」**。

**代码层面的机制（`composite.hlsl:19-54`）——这一条是分析，不是猜测**
```hlsl
float3 bg = 0;
if (!s.captured && Timing.w > 0.5) { bg = background(...); bg *= s.toward; bg += s.star; }
float3 col = bg * s.trans + (1.0 - exp(-s.emit * expo));   // ← 前面一项靠背景，后面一项不靠
return float4(col * alpha, alpha) * saturate(Extra.w);
```
- **盘的自发光** `1 - exp(-emit·expo)` **完全不依赖背景** → 所以 3 里盘和那圈爱因斯坦环还在
  （爱因斯坦环来自盘的二次像，属于 `emit`，不属于 `bg`）。
- **随背景一起消失的只有 `bg * s.trans`**（被弯折的桌面）与**星场** `s.star`
  （星场虽然自带光，但它被塞在同一个 `Timing.w > 0.5` 门里）。
- 结论：**这不是崩溃，也不是取值错误，而是当前设计的必然结果 ——
  v2 的观赏性过度依赖「桌面上正好有东西可以折射」。**
  要消掉这个落差，必须给黑洞提供一条**不依赖桌面内容**的光源。

**候选修复方向（不再是「找 bug」，而是补一条不依赖背景的光源）**

| # | 方向 | 说明 | 代价 |
|---|---|---|---|
| **A** | **星场解耦 + 默认给一点亮度** | 把 `s.star` 从 `Timing.w` 门里移出来（它是自发光，不该受「是否抓屏」控制），并给默认预设一点 `StarGain`。任何背景下都有可被弯折的内容，正是 3 → 2 之间缺的那一环 | 小；但要在 UI 上说清「星星不是桌面的」 |
| **B** ✅ **已选（2026-09-22）** | **补一层程序化背景光（星云 / 辉光）** | 新增一段着色器：不依赖抓屏内容，自己生成一层有层次的背景光，再交给同一套测地线去弯折。观感最接近 `2.jpg` 里成片的光环层次 | 中；需新增着色器代码 + 一个新配置项 |
| **C** | **自动曝光**：背景越暗越抬 `DiskGain` / `Exposure` | 让盘本体在暗背景下更亮 | 小；但不能还原「被折射的桌面纹理」那种层次感 |
| **D** | **保持物理正确，只在 UI 说明** | 承认「暗背景就没特效」 | 零；❌ 已否（你说「特别难看」） |

### B 方案的触发方式：**常开**（已定，2026-09-22）

> 你的原话：「不能让他保持那样吗」→ **要的是「任何时候都长这样」，而不是「缺了才补」**。
> 所以是**常开**：程序化背景光始终参与合成，观感不随桌面明暗改变。

**这让一个担心可以排除掉** —— 起初我担心「常开」会在亮桌面上雾蒙蒙、弄脏 `2.jpg` 的清晰层次。
但看 `composite.hlsl:46,54` 的合成式 `final = col·alpha + desktop·(1 - alpha)` 就知道：
- 黑洞附近 `alpha ≈ window ≈ 1` → 桌面本来就**被完全盖住**，`col` 是什么就是什么。
- 也就是说这层光填的是「本来就空着的地方」，**不会把真实桌面弄脏**；
  只有 `alpha < 1` 的外圈才谈得上叠加，而那里本来就该淡出。

因此「常开」是安全的：暗背景时它把 `2.jpg` 的效果补回来，
亮背景时它与真实折射并存（区域不同：一个在 `alpha≈1` 的内区，一个在渐出区）。

**代价**：这样一来，黑洞的观感几乎完全由程序化层决定，
「把真实桌面吸进去」的存在感会被稀释 —— 需要在两者间给一个可调权重。

### B 方案的技术约束（实现前必须处理）

1. **必须放在 `Timing.w` 门之外**：现在 `bg` 与 `s.star` 都在
   `if (!s.captured && Timing.w > 0.5)` 里（`composite.hlsl:20`）。
   这层程序化光是**自发光**，不能被「是否抓屏」开关掐掉，否则在正是需要它的场景下失效。
2. **不能乘 `s.toward`**：`toward` 是给「真实桌面被过度弯折」做淡出用的，
   程序化光不受这条规则约束。
3. **要能被 `trans` 遮挡**：它代表「黑洞背后的星空」,所以应与 `bg` 一样乘 `s.trans`,
   —— 盘前面的星云要被盘挡住，才不会显脏假。
4. **落入视界的光线不能出光**（`s.captured` 为真时不贡献），否则阴影就不纯黑了。
5. **需要一个独立开关 + 强度滑块**（建议键名 `NebulaGain`，范围 0–1），
   并在「渲染」分区给出控件——沿用 M5.1 的做法。

> ⚠️ **顺带必修的关联项**：采纳 B 时务必同时确认
> `BlackFrameDetector` 判离线**不再关掉整扇 `Timing.w` 门**（至少要把自发光部分摘出来），
> 否则纯黑背景下加了星云也会被拍灭 —— 这是 A/B 两条共用的前置修复。

**候选原因（按可疑度排序）**

| # | 候选 | 代码位置 | 说明 |
|---|---|---|---|
| **a** | **全黑帧检测误判 → 整个扭曲层被跳过** | `Capture/BlackFrameDetector.cs`、`OverlayController`、`composite.hlsl:20` | 判据是「覆盖层窗口内**所有**像素三通道 ≤ **6**，连续 3 帧」。**暗色壁纸 / 暗色 IDE / 深色视频**下极易命中。一旦命中，`Timing.w` 相关分支全关：背景取样、星场、色差全部消失，只剩盘本体。<br>**已在本次冒烟日志里实测触发过**：`抓屏结果为全黑（可能在播放受保护内容），已临时跳过扭曲层` → 数秒后 `抓屏画面恢复正常，扭曲层已恢复` |
| **b** | **盘的自发光被 `alpha` 缩放** | `composite.hlsl:41,45-46,54` | `col = bg*trans + emit`，`alpha = max(window, 1-trans)`，最后 `col * alpha`。远处的盘（`plen` 大 → `window` 小；盘薄 → `trans` 高 → `diskAlpha` 低）会让 `emit` 被**远场淡出窗口**吃掉。`window = exp(-(plen/7)²)` 在 7 个阴影半径处只剩 0.37 |

| **d** | **抓屏降级到 GDI 后的色彩/亮度差异** | `Capture/*` | 本次冒烟实测 `抓屏降级=True`（DXGI 不可用走 GDI BitBlt），两条路径的伽马/色彩空间未必一致，可能导致「有时亮有时暗」 |

## 问题 2：默认大小下黑洞周边有很多圈亮环

**现象**（你的原话）
> 默认黑洞大小会出现黑洞周边有很多圈亮环的情况，事实上应该只有一圈的。

**证据**：`bugs/1.jpg`（Inferno）、`bugs/2.jpg`（Quasar）—— 都是**等间距、细密、延伸到窗口边缘**的同心环。

**关键观察**：这些环**延伸得比盘外径远得多**（Gargantua 的 `rout = 7 r_s` 约等于 2.7 个阴影半径，
而照片里的环一直铺到窗口边缘）。所以它们**大概率不只是盘上的条纹**，而是背景被反复折射的结果。

**候选原因（按可疑度排序）**

| # | 候选 | 代码位置 | 说明 |
|---|---|---|---|
| **a** | **`mirrorUV` 镜像平铺造成背景重复** | `lens.hlsl:11-15` | 反投影把 uv 推到 0..1 之外时，`mirrorUV` 会**镜像重复**整张底图。重复的镜像图案层层嵌套，正好表现为「一圈圈同心结构」。这是**最像照片观感**的一条 |
| **b** | **薄盘多次穿越的多重像** | `lens.hlsl:68-77` | 侧视（`incl ≈ 1.5`）时一条光线会多次穿过盘面，每次 `emit += sh.rgb`。物理上确实该有多重像，但**次数/权重可能偏多**；参考实现只呈现一圈明显的环 |
| **c** | **螺旋条纹经透镜拉伸后的混叠（摩尔纹）** | `disk.hlsl` 的 `swirl`/`vnoiseWrapY`、`DiskWinding = 7` | 1.jpg 的环**间距均匀且极细密**，非常像条纹采样混叠，而不是物理多重像 |
| **d** | **窗口边缘羽化形成可见的环** | `composite.hlsl:48-51` | `smoothstep(fadeR*0.70, fadeR, plen)` 在窗口半径 70% 处开始收尾。M5.1 已记录：1440p 默认参数下窗口半径**顶到 512 上限**，这个羽化会落在离黑洞不算远的位置 —— 可能被看成「多出来的一圈」 |

## 问题 4：关闭引力透镜后出现一大圈黑色（2026-09-23 新增）

**现象**（你的原话）
> 关闭引力透镜之后每个黑洞周边都会直接出现一大圈黑色，不过关闭时它周边的炫彩足够好看，可以保留炫彩、删除黑色，同时给炫彩加上一些变化。

**代码层面的机制（`composite.hlsl`）——这一条是分析，不是猜测**

```hlsl
float3 bg = 0;
if (!s.captured && Timing.w > 0.5) { bg = ...; }        // 透镜关 → bg = 0
float3 col = bg * s.trans + (1.0 - exp(-s.emit * expo)); // 只剩盘的自发光
float diskAlpha = saturate(1.0 - s.trans);
float alpha = saturate(max(s.window, diskAlpha));        // ← 问题在这
```

- `s.window = exp(-(plen/7)²)` 描述的是**「折射层」的覆盖范围**，一直铺到约 7 个阴影半径处。
- 关掉透镜后 `bg` 归零（正确），但 **`alpha` 里的 `window` 项没有被门控** ——
  于是从阴影外缘一直到 7 个阴影半径，覆盖层都在用 **rgb ≈ 0、alpha ≈ 0.98→0.37** 往桌面上涂**黑色**。
- 这就是"一大圈黑色"：**它不是阴影，是折射层的 alpha 在没有内容时留下的黑晕**。
  （而"炫彩"= 盘的自发光 + 星云，两者都不依赖抓屏，所以确实该保留。）

**候选原因（按可疑度排序）**

| # | 候选 | 代码位置 | 说明 |
|---|---|---|---|
| **a** | **`alpha` 里的 `window` 项没跟 `bg` 同生共死** | `composite.hlsl`（`alpha` 那一行） | 主因。`window` 是"折射层覆盖"，透镜关掉后它仍在贡献 alpha，却没有任何颜色可画 |
| **b** | 覆盖层窗口半径按 6 倍阴影半径预留 | `OverlayGeometry.FarFieldRadiusFactor = 6.0` | 决定这圈黑能铺多大；与黑洞本体尺寸无关，所以洞越大黑圈越大 |
| **c** | 抓屏被判全黑时也会退化成同样的黑圈 | `Capture/BlackFrameDetector.cs` | 与问题 1 的候选 **a** 同源：即使透镜**开着**，只要判离线命中，同样只剩 alpha → 黑圈 |
| **d** | 星云（问题 1 新增）不足以盖住这层黑 | `common.hlsl` 的 `nebula()`、`NebulaGain` 默认 0.45 | 星云在门之外，理论上会补光；能否盖住取决于增益与方向，**实测为准** |

**取证方案**
1. 关掉透镜，用 `FarFieldProbePS` / 直接渲 `CompositePS`，量 **2 ~ 7 个阴影半径**处的像素：
   若 rgb ≈ 0 而 alpha > 0 → 坐实 a。
2. 把 `NebulaGain` 从 0 拉到 1 看黑圈是否变淡 → 量 d 的权重。
3. 手动把 `BlackFrameDetector` 判离阈值调到 0（永不触发）再复现 → 分离 c。

**处置方案（候选）**
- **a（必做）**：让 `window` 项由"确实画了背景"来驱动 ——
  `float bgAlpha = Timing.w > 0.5 ? s.window : 0.0;`，`alpha = max(bgAlpha, diskAlpha)`。
  更根本的说法：**折射层的覆盖范围与折射层的内容必须同生共死**。
- **保留项（不动）**：阴影本体（`captured` / `1 - trans` 的那份 alpha）、盘自发光、星云 —— 这些就是你说的"炫彩"。
- **炫彩加变化**：已定并做完 —— 选的是「时间上的流动」，见下方
  「✅ 问题 4「炫彩时间流动」已做（2026-09-24）」。
- c：与问题 1 的 a 合并处理（判离线不得掐掉自发光层，同样也不该留下纯 alpha 的黑圈）。

**验收标准**
- 关闭透镜后，沿半径的亮度剖面在 **2 ~ 7 个阴影半径**范围内与桌面原亮度差异 < 5%（不再有黑晕），
  而环带附近仍有可见炫彩。
- 开启透镜时行为不变（`window` 照旧生效）。

### ✅ 问题 4 核心已修（2026-09-23）：拆开「阴影」与「折射层覆盖范围」

**结论**：主因坐实为候选 **a**。对照实验给出了直接证据 ——
关掉透镜（并关掉盘/星云/星场）后，**2 个阴影半径处的 alpha = 235/255**，
也就是覆盖层把桌面**盖掉了 92%**，而那一层里没有任何颜色可画，于是显形为一整圈黑。

**改动**（`composite.hlsl`）
```hlsl
float bgAlpha    = Timing.w > 0.5 ? s.window : 0.0;   // 折射层：范围与内容同生共死
float shadowAlpha = s.captured ? 1.0 : 0.0;           // 阴影：属于黑洞本体，不受透镜开关影响
float alpha = saturate(max(max(shadowAlpha, diskAlpha), bgAlpha));
```
关键点是**把「阴影的 alpha」和「折射层的 alpha」拆开**：
以前阴影之所以是黑的，是因为 `alpha = max(window, …)` 里 `window` 在中心恰好≈1 ——
代价是这份 alpha 一直铺到 7 个阴影半径，黑的范围被放大了 7 倍。
现在阴影由 `captured` 单独保证不透明，折射层只在真的画了背景时才占 alpha。

**保留不动**：盘自发光 `emit`、星云 `ambient`（都不依赖抓屏）—— 也就是你说的"炫彩"。

**测试**（新增 `tests/LensToggleTests.cs` 4 项，全量 **549 通过 / 0 失败**）
- `LensOff_DoesNotBlanketTheDesktop`：关透镜后 2/4/6 个阴影半径处 alpha < 8
  （**已做 before/after 对照**：旧逻辑 235 → 新逻辑 < 8）
- `LensOff_StillShowsAnOpaqueShadow`：阴影本身仍不透明且为纯黑（防"修过头把黑洞也修没了"）
- `LensOn_StillCoversTheDesktop`：开透镜时行为不变（同时保证上一条不是靠 alpha 整体归零蒙混过关）
- `LensOff_KeepsTheDiskGlow`：关透镜后盘的炫彩仍在

**✅ 「给炫彩加上一些变化」已做（2026-09-24）**：你选的是**时间上的流动**
（星云沿方位角缓慢漂移 + 约 25 秒周期的明暗呼吸，且不受盘速度门控 ——
所以把 `DiskSpeed` 调成 0 冻结盘时，画面照样在动）。
与问题 6 的「星云加变化」确实是同一件事，两处都已落地：见本文件后面的
「✅ 问题 4「炫彩时间流动」已做」与「✅ 问题 6「预设带星云色调」已做」。

## 问题 5：引力透镜的实机效果很差（抖动剧烈 / 根本算不上黑洞）（2026-09-23 新增）

**现象**（你的原话）
> 引力透镜的实机效果并不好，甚至可以说是烂了，移动鼠标时抖动剧烈，而且那个效果根本算不上是黑洞的效果。

这两句是**两件事**，要分开查：**抖动**是时序问题，**不像黑洞**是映射/观感问题。

**候选原因（按可疑度排序）**

| # | 候选 | 代码位置 | 说明 |
|---|---|---|---|
| **a** | **抓屏延迟 → 背景与窗口不同步** | `Capture/*`、`OverlayController` | M6.1 实测**抓屏占整帧约 95%**（24.35 / 24.98 ms，整帧约 40fps）。窗口每帧跟着光标移动，而抓屏内容是**上一帧**的 → 背景在窗口内相对滑动 → **抖动的直接来源** |
| **b** | **抓屏区域随窗口移动，内容每帧都变** | `OverlayController`（按光标所在显示器 + 窗口矩形抓屏） | 与 a 同源：窗口位移 → 取样区域位移 → 折射结果整体平移，观感就是"抖" |
| **c** | **抓屏降级到 GDI** | `Capture/*`（本次冒烟实测 `抓屏降级=True`） | GDI BitBlt 与 DXGI 的色彩/时序本来就不一致，内容不稳 |
| **d** | **天空平面映射本身就不物理** | `lens.hlsl`：`LENS_DEPTH = 13.0`、`window = exp(-(plen/7)²)` | 参考实现注释直言这是 **deliberately unphysical**（为的是"桌面不跟着洞晃"）。代价：它更像**局部放大镜/马赛克**，而不是黑洞。**这可能是"算不上黑洞效果"的根本原因** |
| **e** | 折射集中在环附近、远场快速衰减 | 同上 `window` | 只有中心一小块有折射 → 不像黑洞，像局部扭曲 |
| **f** | 多圈亮环让画面显脏 | 问题 2 | 与问题 2 叠加，观感更差 |

**取证方案**
1. **先分开"内容变了"还是"位置抖了"**：用「截图补偿」当探针（问题 1 用过这招），
   在同一鼠标位置连续合成两帧量差异；再把鼠标匀速移动一段，量背景在窗口内的逐帧位移。
2. 把**抓屏耗时与滞后帧数**打进日志，确认 a。
3. **冻结窗口位置**（鼠标不动 / 临时关掉跟随）看还抖不抖 —— 若只在移动时抖，锁定 a/b。
4. 单独把 `LENS_DEPTH` 从 13 调大到 30~40 看观感是否更像黑洞 → 验 d。
5. 在 M6.1 的自动降档日志里确认真跑的是哪一档步数（24/48/88），排除"降档把画面搞糊"这种假象。

**处置方案（候选，三条路线，需你先定方向）**
- **路线 1（治抖）**：抓屏与渲染解耦 —— 缓存一帧较大的抓屏区域，窗口移动时复用 + 脏矩形增量更新；
  必要时降低抓屏频率（它已是 95% 的瓶颈）。
- **路线 2（治观感）**：承认"在桌面抓屏上做全屏黑洞"有天花板 —— 加大 `LENS_DEPTH`、
  放缓 `window` 衰减、把折射收成**一圈**而不是一团（与问题 2 同向）。
- **路线 3（重新定位）**：如果结论是"桌面透镜做不出黑洞观感"，就得重新定目标 ——
  是继续做「桌面透镜光标」，还是把重心放到**盘 + 环 + 星云**的造型上，透镜只做辅助。

### 执行记录 · 抖动那一半（2026-09-23）

**第一刀（你做的）：整屏固定抓屏** —— 抓整块显示器，纹理锚在显示器坐标上，
窗口/黑洞怎么动都不影响它。这一刀消灭了「抓屏区域跟着窗口跑」造成的相对滑动。

**但只做这一刀不够，实测仍抖。** 于是加了逐帧诊断（`--jitter-log`，见下）定位。

**取证方法（可复用）**：新增启动开关 `--jitter-log`，逐帧输出
`鼠标 / follow / 窗口 left,top,extent / 黑洞在窗口内的 center / 抓屏耗时 / 抓屏纹理偏移`。
再用脚本驱动鼠标匀速横移，把日志拉回来分析 —— 不靠眼睛，靠数据。

**诊断结论（两条，都很关键）**

1. **坐标映射是精确的，不是抖动的来源**。逐帧数据里
   `left` 与鼠标严格同步、`center=436.00` 恒定、`mapOffset` 与窗口严格对应
   （例如 left=336/1920 → 0.17500，left=1154/1920 → 0.60104）。
   所以「亚像素错位 / 量化抖动」这类怀疑**全部排除**。
2. **真凶是抓屏把帧率压到了 ~20FPS**。逐帧抓屏耗时 **33–68ms（均值 ~46ms），占整帧约 95%**。
   黑洞只能以 20Hz 更新，鼠标一动就一格一格地跳 —— 观感上就是「左右摇摆」。
   ⚠️ 整屏抓屏虽然修对了抖动机制，却把抓屏面积从 872² 放大到 1920×1080，
   耗时翻了一倍多（原 ~21ms → ~46ms），是**用帧率换正确性**。

**第二刀（本次补上）：把抓屏变便宜**

| 改动 | 说明 |
|---|---|
| `GdiDesktopCapture` 复用 `Bitmap` | 原来每帧 new 一块 1920×1080×4 ≈ **8MB** 的 Bitmap，光分配+GC 就很贵。尺寸不变时复用，只重新 BitBlt（46 → 38.7ms） |
| 抓屏**自适应节流** | 纹理锚在显示器上，**只有桌面内容变了才需要重抓**；黑洞/窗口移动不需要重抓。间隔 = 上次抓屏耗时 × 3，钳制在 [1/60, 1/10] 秒。自适应是为了不误伤快机器（那边 DXGI 抓屏只要 1ms，不该被节流） |

> ⚠️ **踩坑**：第一版把间隔写死 1/30 秒（33ms）**完全没生效** —— 帧间隔本身就是 47ms > 33ms，
> 阈值永远够不着。鸡生蛋：正是因为抓屏慢，帧才慢。必须让间隔显著大于当前帧间隔才有用。

#### ⚠️ 第二刀是错的（你的判断成立，已作废）

> 你的原话：「没那么抖了，但是同时背景帧率暴降，实际上不那么抖就是因为帧数暴降吧，你并没有解决问题」

**你是对的，认了。** 节流把桌面内容的刷新率从 20Hz 压到 **10Hz** ——
抖动看起来少了只是因为**更新次数少了**，是拿新鲜度换流畅，不是修好。
下面那张表里的「帧率提升」是真的，但代价是背景内容滞后，不能算修好。

#### 第三刀（现在的做法）：不节流，改成**每帧少抓一点**

思路：抓屏纹理仍然**整块显示器大小、锚在显示器坐标上**（位置无关 → 不会抖），
但每帧只把「窗口附近那一块」增量 Blit 进纹理的对应位置
（`IDesktopCapture.TryCapture` 新增 `destX/destY`，用带 `Box` 的 `UpdateSubresource` 写局部）。
区域小得多 → 单帧便宜 → **可以每帧都抓，桌面内容保持新鲜**。

**实测结果**（同一台机器、同一脚本驱动鼠标横移）

| 方案 | 渲染帧率 | 背景内容刷新 |
|---|---|---|
| 最初（整屏逐帧抓） | 20.4 FPS | 20 Hz |
| 第二刀（整屏 + 节流）**已作废** | 43 FPS | **10 Hz** ❌ |
| 第三刀（局部抓屏 25% 余量） | 30 FPS | 30 Hz |
| **第三刀（局部抓屏 5% 余量）✅ 当前** | **39 FPS** | **39 Hz** |

即：帧率与「第二刀」几乎持平（39 vs 43），但**内容新鲜度是它的 4 倍**。

**顺带修掉/查清的其他事**
- `GdiDesktopCapture` 原来每帧 new 一块 1920×1080×4 ≈ **8MB** 的 Bitmap，改为尺寸不变时复用。
- **为什么 DXGI 用不了（已查证）**：即使把设备建在「驱动桌面的那块适配器」上
  （原先用 `IntPtr.Zero` = 适配器 0，双显卡机上常不是驱动显示器的那块；
  且指定适配器时 `DriverType` 必须是 `Unknown`，否则 `E_INVALIDARG`），
  `DuplicateOutput` 仍返回 `DXGI_ERROR_UNSUPPORTED(0x887A0004)`。
  本机只有 1 个适配器 1 个输出 —— **系统层面不支持桌面复制，应用层改不了**。
  相关失败原因现在会打进日志（原来静默吞异常，无从排查）。
- 测试替身（`RecordingCapture` / `SolidColorCapture`）此前用小缓冲 + `null` Box 写整块纹理
  → **越界崩溃（AccessViolationException）**，已全部改为传 Box。

**剩余瓶颈**：GDI 抓屏 ~22ms。⚠️ **原以为「抓 0.9M 像素要 22ms」是错的** ——
2026-09-24 实测：耗时与面积无关、与是否复用 DC 也无关，3 种调用方式 × 2 种面积**全部卡在 ~17ms**
（≈ 一个 60Hz 周期），这是 **DWM 合成同步等待**，不是像素拷贝。
因此「半分辨率抓屏」**实测证伪**（面积降到 1/4，这 17ms 照付），DXGI 又硬件不可用。
→ 唯一出路是**抓屏搬后台线程**，你决定留到下一轮。详见文末「性能：已归因」。

### ✅ 问题 3「混合预览」已做（2026-09-24）

### ⏸️ 性能：已归因，暂不动（下一轮再定）

整帧 16–20ms 里抓屏占 12–18ms，本轮做了一次完整归因，**结论是它压不下去**。

**实测（本机，GDI 三种调用方式 × 两种面积）**

| 调用 | 526² | 1052² |
|---|---|---|
| `Graphics.CopyFromScreen` | 16.57 ms | 23.55 ms |
| `BitBlt` 复用 DC（P/Invoke） | 16.61 ms | 19.22 ms |
| `BitBlt` 每次 `GetDC` | 17.01 ms | 17.79 ms |

耗时**与面积无关、与是否复用 DC 无关**，全都卡在 ~17ms ≈ 一个 60Hz 周期 ——
这是 **DWM 合成同步等待**，不是像素拷贝。于是两个看起来很自然的优化都被证伪：

- ❌ **半分辨率抓屏**：面积降到 1/4，这 17ms 照付
- ❌ **改用 P/Invoke + 复用 DC**：同样 16.6ms（`CopyFromScreen` 的开销并不在 DC 获取上）

**那 DXGI Desktop Duplication 呢？本机用不了**（临时探针实测，跑完即删）：

```

   >>> DuplicateOutput 失败 0x887A0004 DXGI_ERROR_UNSUPPORTED
适配器 #1 Intel(R) UHD Graphics   无任何输出
```

### ✅ 问题 7 已取证定位（2026-09-24）：是 **B**，而且讽刺的是那个「防抖」设置就是抖源

### 🔍 残余抖动已定位（2026-09-24）：根因是**抓屏阻塞主循环**

你实机反馈：*「还是会有一点抖」*，`center` 已经恒定却仍有残余 —— 说明还有第二个源头。

**根因**：抓屏目前在主循环里**同步**执行，耗时 ~17ms 且**波动 5~24ms**：

```
每帧：读鼠标 → Move 窗口 → 抓屏（17ms，波动） → 渲染 → Present
                              ↑ 主循环在这里被阻塞，期间鼠标已经又移动了
```

- 帧时间不恒定 → 从「读鼠标」到「显示出来」的**滞后量不恒定** → 抖；
- 这正好解释了「只有快移才抖」：位移越大，滞后的波动越显眼；慢移时滞后量变化小，看不出来。

**关键发现 —— 参考实现为什么不抖**（`copy/extracted/source/singularity-0.4.0/src/capture_windows.rs`）：

```rust
// Windows desktop capture via Windows.Graphics.Capture (windows-capture crate).
// Runs on its own thread.                      ← 独立线程
// Preferred path: GPU-copy each frame into a shared D3D12 texture (zero CPU round trip)
```

- 抓屏用的是 **Windows.Graphics.Capture**（**既不是 DXGI Desktop Duplication，也不是 GDI**）；
- 跑在**自己的线程**，由 `on_frame_arrived` **回调**驱动（事件式，不是我们主动 polling）；
- GPU 侧零拷贝 `CopyResource` 到共享纹理，fence 完成后才 `version += 1`；
- **渲染侧从不等待抓屏**，只取最新那一帧。

→ 它的渲染循环里**根本没有那 17ms**。

### 🔑 更关键的一点：参考实现是**全屏窗口**，黑洞在窗口内部移动

`copy/extracted/source/singularity-0.4.0/README.md`：

```
- **A real overlay** - fullscreen, always-on-top, click-through
- **Place it anywhere** - hold Ctrl+Shift and the hole follows your mouse
```

也就是说：**窗口本身不动**，黑洞是靠着色器里的浮点 uniform 在窗口内平移的。
于是它从根本上绕开了我们撞上的两个问题：

| | 参考实现（全屏） | 我们（跟随光标的小窗口） |
|---|---|---|
| 窗口位置 | **固定不动** | 每帧 `Move`，受 Win32 整数像素约束 |
| 黑洞定位 | 着色器里的浮点 uniform → **天生亚像素** | 窗口位置 + 局部坐标 → 被量化 |
| 抓屏 | WGC 零拷贝 + 独立线程 | GDI 同步阻塞 ~17ms（波动 5~24ms） |
| 渲染面积 | 全屏，但只有黑洞附近做积分（early-out） | 小窗口（约 460²） |

**所以「完全不抖」有两层原因，而 WGC 只是第二层**：
1. 窗口不移动 → 没有量化、没有滞后；
2. 抓屏零拷贝异步 → 帧时间恒定。

我们就算只做第 2 条（后台抓屏），第 1 条仍然存在 —— 这就是「修完 center 还是有一点抖」的解释。

⚠️ 注意：PRD F5-2 明确要求「覆盖层仍是跟随光标的**小窗口**（非全屏）」，
当初列这条是为了性能（只渲染黑洞周围）。但实测**渲染只占 0.01ms、瓶颈全在抓屏**，
所以「改成全屏」的性能代价可能远小于当初的预估 —— 这需要实测确认。

### 推导：小窗口架构下，两种抖动**不可能同时消除**

设窗口位置 `L`（Win32 整数）、局部坐标 `C`、放大率 `M`（透镜的本质）。

- 黑洞屏幕位置 = `L + C`，要**精确跟随** ⇒ `C` 必须连续变化；
- 背景取样 = `C + g(uv − C)`，`C` 变化 δ 时取样位置变化 **δ·(1 − M)**；
  `M ≠ 1`（尤其折射区 M 很大）⇒ `C` 一抖，折射图案就被**放大**着抖。

所以只有两种分配方式，且互斥：

| 选择 | 黑洞屏幕位置 | 折射图案 |
|---|---|---|
| `C` 连续（修法之前） | 亚像素精确 ✅ | 被放大率放大着抖 ❌ |
| `C` 恒定（当前修法） | 只能按 1px 步进 ❌ | 完全稳定 ✅ |

想两全，唯一办法是**让 `L` 不再变化** —— 也就是窗口固定不动（全屏），
黑洞位置完全交给着色器里的浮点 uniform。这正是参考实现的做法。

顺带一提：我们抓屏已经是「整块显示器固定抓取」（问题 5 的成果），
所以窗口变大**不会**增加抓屏成本，只增加渲染填充面积 —— 而渲染目前只占 0.01ms。

**可行性验证（已做第一步）**：本机 `GraphicsCaptureSession.IsSupported()` = **True**
（系统支持 WGC；与 DXGI DD 返回 `UNSUPPORTED` 形成对比）。

**方案**

| 方案 | 做法 | 代价 |
|---|---|---|
| **A（对齐参考实现）** | 改用 Windows.Graphics.Capture + 独立线程 + 渲染不等待 | C# 侧需要 WinRT / COM 互操作（项目当前 TFM 是 `net8.0-windows`，需改成版本化 TFM），工作量不小 |
| B（保底） | 现有 GDI 抓屏搬到后台线程，渲染不等待 | 改动小、确定能解决抖动并到 60 FPS；背景内容仍滞后约 17ms、上限 60Hz |

**你选**：先验证 WGC 能不能真的建帧池拿到帧，能用就上 A，不能用退到 B。
（临时探针放在项目外 `d:\桌面\wgc-probe`，验证完删除。）

取证前先看日志确认当前跑的是哪条路径。

**代码层面的机制（这一条是分析，不是猜测）**

现在的抓屏是「**整块显示器大小的纹理 + 每帧只增量更新窗口那一块**」（问题 5 第三刀）：

```
OverlayController.cs:676-716
  margin   = rect.Width * CaptureMarginFactor   // 0.05，窗口外扩 5%
  x0,y0,x1,y1 = 窗口 ± margin（再钳到显示器范围）
  destX,destY = (x0,y0) − 显示器原点
  → 只把这一小块 Blit/UpdateSubresource 进显示器尺寸的纹理
```

于是**纹理里「窗口 ± 5%」之外的内容，取决于那块区域历史上有没有被抓过**：
抓过 → 旧内容；**从没抓过 → 保持创建时的值（黑）**。
而透镜的本质就是**把光线投到窗口之外去取样**，所以折射区必然要读这些区域。

**候选原因（按可疑度排序）**

| # | 候选 | 代码位置 | 说明 |
|---|---|---|---|
| **a** | **后台抓屏上传的是「上一帧的区域」** | `OverlayController.cs:693-704`、`BackgroundGdiCapture.cs` | 后台线程抓一次约 17ms（DWM 同步等待），期间窗口已经移走。`SetRegion` 每帧更新，但**上传进来的那一帧对应的是旧区域** → 窗口当前覆盖的**新区域这一帧没被写过** → 仍是纹理初始值（黑）。**移动越快，未覆盖的新区域越大 → 越黑**。这条能同时解释「只在移动时」「只在折射区」 |
| **b** | **`CaptureMarginFactor = 0.05` 的余量不够** | `OverlayController.cs:50,680` | 强偏转（阴影附近）会把取样点推到窗口外很远，超出这 5% 就落到未抓过的区域。静止时因为反复抓过所以没事，移动时会不断碰到新区域 |
| **c** | **纹理重建后整体清零** | `OverlayController.cs:636-648` `CreateCaptureTexture` | 跨显示器移动 / 分辨率变化时纹理重建 → 全部变黑，需要重新填充。表现为「移到另一个屏的瞬间整片黑」 |
| **d** | **全黑帧检测误判** | `Capture/BlackFrameDetector.cs`、`OverlayController.cs:724-727` | 采样原点跟着窗口走；窗口移到未抓过的黑区时判「全黑」→ 跳过扭曲层。与问题 1 的候选 a 同源。**注意**：问题 4 修完后 `bgAlpha` 与内容同生共死，所以 d 单独造成「黑」的可能性已降低，更可能是 a/b 的**结果**而非原因 |
| **e** | **星云/压层的 alpha 在没有内容时铺满** | `composite.hlsl` 的 `bgAlpha`、`lens.hlsl` 的 `backgroundCoverage()` | 若 coverage 判定为「有内容」但取到的像素是黑的，就会画出一整片黑 —— 与问题 4 那个黑圈是同一类「alpha 与内容脱钩」的病 |

**取证方案（按成本从低到高，第 1 条就能定生死）**

1. **纯色桌面判据（最干净，先做这个）**：把桌面临时换成**纯白**（或浅灰）壁纸，
   然后移动鼠标。
   - 折射区出现**纯黑** → 坐实「没抓到内容」（a / b / c），因为白桌面上正常折射**不可能**是黑的。
   - 不黑 → 那是桌面内容本身的问题，回到 d / e。
2. **关掉后台抓屏对比**：临时让 `IsDegraded` 分支不启动（回同步路径）再移动一次。
   黑区消失 → a；仍在 → b / c。
3. **把 `CaptureMarginFactor` 从 0.05 临时调到 0.5** 再移动：黑区消失 → b。
4. **看日志**：确认有没有「抓屏已切到后台线程」（判断 a 是否成立的前提），
   以及有没有「抓屏结果为全黑…已临时跳过扭曲层」（判 d）。
5. `--jitter-log` 里已经有逐帧的 `left/top/captureMs`，再加一列**当前上传区域**，
   与窗口矩形做差 → 直接量出"未覆盖的新区域"有多大。

**处置方案（候选，取证后再定）**

- **a**：后台线程抓的区域要**比窗口大一圈**（预取余量 ≥ 一帧最大位移 + 取样外扩），
  这样滞后量落在余量里而不是窗口里；同时**上传时按该帧自己的 dest 写**（现在就是这样），
  关键是区域要够大。
- **a 的兜底**：从未被抓过的区域**不要留黑** —— 首次启用 / 区域大变时先做一次整屏填充，
  或用星云兜底（星云不依赖抓屏，问题 1 已建好这层）。
- **b**：把 `CaptureMarginFactor` 调大（代价：单帧抓屏面积变大 → 变慢，
  但实测耗时与面积弱相关，见文末「性能：已归因」）。
- **c**：纹理重建后标记「全部脏」，下一帧整屏抓一次。
- **e**：`bgAlpha` 再收紧一层 —— 取到的像素是黑且该区域未抓过时，coverage 也要跟着降。

**验收标准**
- 在**纯白桌面**上以常见速度移动鼠标，折射区**不出现黑块**（亮度不低于周围桌面亮度的 70%）。
- 移动过程中不出现「抓屏结果为全黑…已跳过扭曲层」的日志跳变。

**⚠️ 与问题 7 的关系**：问题 7 的后台抓屏曾抛 `0x80070057`（实机白屏崩溃），
当前是否仍启用**必须先确认**。若现在跑的是同步路径，候选 a 直接排除，优先查 b。

### ✅ 问题 9 取证第一步已完成（2026-09-25）：坐实「没抓到内容」，且**会闪 ⇒ 是逐帧竞态**

**你的观察**：换成纯白桌面后移动鼠标，折射区**会出现黑，而且是一闪一闪的**。

**结论 1 —— 白桌面上的黑块 = "没抓到内容"**
白桌面上正常折射**不可能是黑的**（折射只会搬移桌面像素，不会凭空产生黑色）。
出现纯黑只可能是「取样点落在纹理里从未被写过的位置」。
→ **坐实 a / b / c 这一类**；同时基本排除 **e**（`bgAlpha` 与内容脱钩：那会让
alpha 铺满但取到的仍是白 → 该显白不该显黑）。

**结论 2 —— "一闪一闪"把嫌疑锁定到 a**
这两个候选的表现形态是不一样的，可以靠"闪不闪"分开：

| 候选 | 预期表现 |
|---|---|
| **b**（余量 5% 不够） | 黑区是**固定的一圈**（在窗口外侧某个半径之外），跟着窗口一起平移，**不会闪** |
| **a**（后台抓屏上传的是旧区域那一帧） | **逐帧不同**：某些帧当前窗口区域被写到了、某些帧没有 → **闪** |

观察到的是"闪"，所以主因是 **a —— 逐帧竞态**，不是静态的余量不足。

**顺带排除的一项**：后台路径**不走节流**（`OverlayController.cs:657` 的
`if (_background is null)` 才判断间隔），所以这次的闪**不是**问题 5 第二刀那个节流造成的。

**因果链（当前推断）**
```
后台线程抓一次约 17ms（DWM 同步等待），这期间窗口已经移走
  → SetRegion 每帧更新为「当前窗口」，但 TryUpload 上传的是「上一次抓完的那一帧」
  → 那一帧对应的是旧区域，写进纹理的也是旧 dest
  → 窗口当前覆盖的新区域这一帧没被写过 → 保持创建时的黑
  → 下一帧如果慢/区域对上了就又正常 → 一闪一闪
```

**下一步（待你定方向）**

| 方案 | 做法 | 代价 / 风险 |
|---|---|---|
| **1（直接修 a，推荐）** | 后台抓屏的区域按「窗口 + 一帧最大位移 + 折射外扩」放大（先试 **100%** 余量，即窗口的 2 倍边长）；并做**首帧整屏填充**，杜绝"从未写过"的黑底 | 改动小、只动 `margin` 与一次初始化；余量取多大需要实测 |
| **2（先量再修）** | 给 `--jitter-log` 加一列「本帧上传区域 vs 窗口矩形」，量出未覆盖宽度到底有多大，再反推余量 | 多一轮往返，但余量是算出来的而不是拍的 |
| 3（换架构） | 后台线程改为**始终整屏抓**（不跟窗口区域走），上传时按整屏写 | 17ms 与面积弱相关（见文末性能归因），可能反而更简单；但每帧上传整块 8MB 的开销要实测 |

我倾向 **1 或 3**：3 更简单彻底（区域恒定 → 不存在"旧区域"这个概念），
代价是每帧上传的数据量变大——而抓屏本身的 17ms 与面积无关，
多出来的只是 `UpdateSubresource` 的拷贝时间（局部约 0.3ms，整屏按面积外推约 1ms 量级）。
