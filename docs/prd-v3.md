## 1. 为什么要改

### 1.1 直接触发：两个实机问题修不干净

| 问题 | 现象 | 现状 |
|---|---|---|
| **问题 7** | 移动时折射区抖动 | 已定位到 2px 位置量化并修掉；但**残余抖动**另有源头 —— 抓屏阻塞主循环导致帧时间不恒定 |
| **问题 9** | 移动时折射区变黑、一闪一闪 | 已取证坐实「没抓到内容」，主因是后台抓屏上传的是**旧区域**那一帧，逐帧竞态 |

两条都指向同一个结构：

```
每帧：读鼠标 → Move 窗口（整数像素） → 抓屏（~17ms 波动） → 渲染 → Present
```

### 1.2 根本原因：小窗口架构下，两种抖动**不可能同时消除**

`fixes-v2.md` 里已有完整推导，这里只放结论。设窗口位置 `L`（Win32 整数）、局部坐标 `C`、透镜放大率 `M`：

- 黑洞屏幕位置 = `L + C`，要精确跟随 ⇒ `C` 必须连续；
- 背景取样位置 = `C + g(uv − C)`，`C` 变化 δ 时取样点变化 **δ·(1 − M)**；
- `M ≠ 1`（折射区 M 很大）⇒ `C` 一抖，折射图案就被**放大**着抖。

于是只有两种分配方式，且互斥：

| 选择 | 黑洞屏幕位置 | 折射图案 |
|---|---|---|
| `C` 连续 | 亚像素精确 ✅ | 被放大率放大着抖 ❌ |
| `C` 恒定（当前实现） | 只能按 1px 步进 ❌ | 完全稳定 ✅ |

**想两全，唯一办法是让 `L` 不再变化 —— 也就是窗口固定不动。**

再加上抓屏滞后（17ms 且波动 5~24ms）造成的**滞后量不恒定**，
小窗口架构下这就是一条硬天花板，调参只能缓解，不能消除。

### 1.3 结论

> **把黑洞从「跟随光标的小窗口」搬到「固定不动的全屏窗口」，位置完全交给着色器 uniform。**

这一改同时吃掉问题 7 与问题 9：
- `L` 恒定 ⇒ 没有量化、没有 Move；
- `C` 是浮点 uniform ⇒ 天生亚像素，不用再二选一；
- 抓屏区域 = 整块显示器且恒定 ⇒ 不存在「旧区域」竞态。

## 2. 目标架构

| | 现在（v2） | 目标（v3） |
|---|---|---|
| 窗口 | 跟随光标的小窗口，边长 = 2 × 6 × 阴影半径 | **全屏（= 显示器矩形），永不移动** |
| 黑洞定位 | 窗口位置 + 窗口内局部坐标 | **着色器 uniform（全屏 uv），浮点、亚像素** |
| 窗口移动 | 每帧 `Move` + 整数像素量化 | **不再移动** |
| 合成 | 小窗口 per-pixel alpha 与桌面混合 | **全屏窗口 + 保持透明，只在黑洞附近输出 alpha**（保留问题 4/5 的修复） |
| 光栅化 | 仅窗口面积（约 418²） | **整屏光栅化 + 着色器内 early-out** |
| 抓屏区域 | 整块显示器（问题 5 成果），但每帧只更新窗口 ±5% | 整块显示器，**区域恒定**（本步先不动） |
| `CaptureMap` | 窗口 uv → 显示器 uv 的仿射映射 | 窗口 = 显示器 ⇒ **退化为恒等**（本步先保留计算） |
| 多显示器 | — | **本轮不管**，先单显示器 |

## 3. 已定决策（逐条记录）

| # | 议题 | 决策 |
|---|---|---|
| 1 | 光栅化范围 | **照搬参考实现**：整屏光栅化，靠着色器内 `b >= bmax` 分支让远处像素走解析式，不做 CPU 侧裁剪/scissor |
| 2 | 合成方式 | **全屏窗口 + 保持透明**。整屏清成透明，只在黑洞附近输出 alpha；现有合成逻辑与问题 4/5 的修复**全部保留** |
| 3 | 多显示器 | **本轮不考虑**，按单显示器一个全屏窗实现 |
| 4 | 实施节奏 | **分步**。第一步只做「窗口变全屏 + 黑洞位置改 uniform」，实机确认抖动/变黑消失并测帧率后，再动连带项 |
| 5 | 是否保留小窗口路径 | **不保留**。直接换成全屏，删掉旧路径；出问题用 git 退回 `8455e44` |
| 6 | 帧率不达标时 | **先不动**。反正瓶颈一直在抓屏（17ms），先把抖和黑解决掉验收，性能统一留到「抓屏搬后台线程」那步 |
| 7 | R1 自反馈 | **改之前先单独验一次**：在现有代码上临时把窗口拉成满屏，确认抓屏没抓到自己，再正式改（跑完还原） |

> 决策 2 的取舍已向你说明：照搬参考实现的「全屏不透明、由我们画整个桌面」能让
> 问题 4/5 的 alpha 类修复自动作废，但抓屏质量会直接决定**整屏**画面。
> 你选择保留透明与现有合成逻辑，代价是那些 alpha 坑继续存在。

## 5. 第一步范围（本次只做这些）

### ✅ 做

1. **窗口改为全屏**：矩形 = 光标所在显示器的矩形（`ScreenMetrics.MonitorRectAt`），
   创建后不再 `Move`；尺寸只在显示器/分辨率变化时重建。
2. **黑洞位置改 uniform**：`centerX/centerY` = 跟随后的**绝对屏幕坐标**
   （换算到窗口内坐标 = 显示器内坐标），传给着色器的仍是 uv。
   惯性跟随 / 静止游荡逻辑**不变**，它们本来就输出连续浮点位置。
3. **删掉"窗口跟着光标跑"这条链路**：`OverlayController.Tick` 里按 `_follow` 计算窗口矩形并
   `Move` 的部分不再执行（或退化成只在显示器变化时更新）。

### ❌ 本次不做（后续步骤）

- 抓屏（区域、后台线程、节流）——问题 9 的修法，`fixes-v2` 里已有三个候选方案待定
- 截图补偿（M4）中依赖「窗口矩形」的部分
- 预览（`PreviewSurface` / `OverlayGeometry.PreviewFit`）的适配
- 多显示器
- 性能裁剪（若实测撑不住再加 scissor）
- 死代码清理

| 模块 | 现在 | 要改成 | 备注 |
|---|---|---|---|
| `OverlayGeometry.ComputeV2WindowRadius` | 决定窗口边长 | **不再决定窗口尺寸**；但远场半径仍要用于着色器羽化 | `FarFieldRadiusFactor = 6.0` 保留 |

| `BlackFrameDetector` 采样原点 | 窗口中心 − 显示器原点 | 改为黑洞所在处 − 显示器原点 | 第一步需跟着改，否则采样点固定在屏幕中心 |
| `IOverlayWindow.Move/Resize` | 每帧调用 | 只在尺寸变化时调用 | |
| 着色器 `lens.hlsl` | `window = exp(-(plen/(7·rh))²)`、越界淡出 | 基本不变 | 远场衰减天然让 alpha → 0，正好满足「只在黑洞附近输出 alpha」 |

| PRD F5-2 | 明确要求「跟随光标的**小窗口**（非全屏）」 | **作废**，本文取代 | 当初理由是性能（只渲染黑洞周围）；实测**渲染只占 0.01ms、瓶颈全在抓屏**，该理由已不成立 |

## 8. 验收标准（第一步）

| 项 | 标准 |
|---|---|
| 窗口 | 尺寸 = 显示器矩形；连续多帧 `left/top/extent` **完全不变**（即使光标大幅移动） |
| 黑洞位置 | 随光标连续变化，**不再被量化**（拖慢速移动时位置应逐帧平滑推进） |
| 抖动 | 匀速拖动鼠标时，折射区不再抖（`--jitter-log` 里 `center` 平滑单调） |
| 变黑 | 纯白桌面上移动，折射区不出现黑块 / 闪烁 |
| 帧率 | 实测记录即可（整屏 2M 像素，预期会降；降多少决定要不要加裁剪） |
| 回归 | `dotnet build -c Release` 0 警告 0 错误；`dotnet test` 全绿 |

## 9. 风险与必须先验证的项

| # | 风险 | 说明 |
|---|---|---|
| **R1** | ~~全屏透明窗被自己的抓屏抓到~~ | ✅ **已验通过（2026-09-25，P0）**。用洋红对照实验证明 `WDA_EXCLUDEFROMCAPTURE`（回读 = 0x11）**对 GDI BitBlt 同样生效**：不设时截屏整屏可见（采样点 32400），设上后**采样点 0（完全不可见）**。而我们的抓屏走的正是同一条 BitBlt 路径 ⇒ 全屏窗不会形成镜像回廊。方法与数据见 `plan-v3.md` 的 P0 |
| **R2** | ~~性能~~ | ✅ **实测不是问题（2026-09-25，P0）**。全屏 **1920×1080**（物理像素；`fixes-v2` 里那个 1280×720 是 150% 缩放下的**逻辑**分辨率）⇒ 2.07M 像素，比小窗口的 0.17M **约 12 倍**。结果帧率 **56.4–57.3 FPS**，分段：抓屏 0.56–0.94 / 渲染 **0.01–0.02** / Present 0.96–3.75 / 整帧 1.68–4.60 ms。12 倍像素涨幅落在 GPU 上，而渲染只占 0.01ms ⇒ **瓶颈从来不在渲染**。比改动前的 52 FPS 还快，因为抓屏已搬后台线程 |
| **R3** | **layered 窗上重建 swapchain 会失败** | 参考实现 `main.rs:757-763` 明确警告。全屏窗尺寸变化（换分辨率 / 换显示器）时必须谨慎，尽量跳过无意义的重建 |
| **R4** | **星云 alpha 失控** | 全屏下「一圈 alpha=1 的星云」若范围变大，会变成大面积不透明。**第一步必须复核** |
| **R5** | **窗口边缘羽化失效** | fadeR 变成屏幕半高后，原本用来收尾的羽化等于没有；需确认画面边缘（靠屏幕边时）不会出现硬边 |
| **R6** | ~~第一步之后问题 9 可能仍在~~ → ✅ **已确认自动解决（2026-09-25）** | 窗口变成显示器矩形后，`x0 = max(rect.Left − margin, monitor.Left)` 因 `rect.Left == monitor.Left` 而恒等于 `monitor.Left`（右边同理），**抓屏区域自动 = 整块显示器且恒定**，「旧区域」竞态从根上消失。实机确认：**变黑不再出现**。代价：每帧抓的面积变大，但由后台线程承担 —— 实测抓屏仅 **0.78ms**、整帧 3.46ms、56.9 FPS |
