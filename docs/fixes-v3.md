## 问题 1 — 透镜边缘模糊：透镜效果没有完全覆盖原画

**你的反馈**：*「在引力透镜的边缘会出现一点模糊的问题 就是透镜的效果没有完全覆盖原画」*
**证据**：`bugs/边缘bug.jpg` —— 主界面右侧，黑洞外围一圈的文字出现**重影**
（「距离越大跟随越快」那段文字能同时看到两个错位的拷贝）。

**初步定位（待取证确认）**

重影 = **半透明的「偏移画面」叠在真实桌面上**。两个条件同时满足才会出现：
位移 ≠ 0（画面被弯折）**且** alpha < 1（桌面从底下透出来）。

v3 全屏之后这两个条件恰好在一个环带上同时成立：

```
composite.hlsl 的两条淡出曲线在全屏下的位置：

位移淡出  window = exp(-(plen/7)²)        → 7 rs 处仍有 37%，9 rs 后才基本归零
alpha 羽化 alpha *= 1 - smoothstep(5.83, 8.33, plen)   ← 全屏后 fadeR = 8.33 rs
```

⇒ 在 **5.83 ~ 8.33 rs** 这个环带上：alpha 正在往下掉（半透明），
而位移还有 37% 甚至更多（画面明显偏移）→ 偏移的画面半透明地叠在真实桌面上 → **重影模糊**。

- 小窗口时代**没有**这个问题：当时 `fadeR` 只有 3.2 rs，alpha 在位移还很大的地方
  就已经切没了（P1.4 的「意外收获」：小窗口其实一直在切掉透镜）—— 切得干脆，看不到混合过程。
- 全屏把可见范围扩到 8.33 rs 之后，这段「半透明 + 还有位移」的环带第一次暴露了出来。

**候选修法（二选一，修复时定）**
- **a. 先归零位移、再淡出 alpha**：把位移的淡出窗口改小（如 `exp(-(plen/4)²)`），
  让位移在 alpha 开始下降（5.83 rs）之前就归零 → 半透明区里画面没有偏移，重影消失。
- **b. 推迟 alpha 羽化**：把羽化区间移到位移充分归零之后（如 10 ~ 12 rs），
  代价是黑洞的「势力范围」再往外扩一圈。

倾向 a：不扩大势力范围，且「先停折射再淡出」物理上更干净。

### ✅ 问题 1 已修（2026-09-26）

**采用方案 a**，并且把它做成可回归的断言而不是「看着像好了」。

**改动**（`lens.hlsl`）
- 位移不再与星云共用 `window`（7 rs 高斯），改用专用的 `windowDisp`：
  ```hlsl
  float windowDisp = 1.0 - smoothstep(fadeR * 0.45, fadeR * 0.68, plen);
  ```
  `fadeR = 0.5 / Hole.x`（视口半高，单位是阴影半径）—— **与 `composite.hlsl` 的羽化同源**，
  所以窗口尺寸 / 洞径 / 预览与全屏全都自动同步，不存在第二处 magic number。
- **远场**（偏折量 `defl`）与**近场**（`spw = p + (sp - p) * …`）两条分支**共用同一个** `windowDisp`
  ⇒ 交界圆上两条分支乘的是同一个数，仍然无缝（否则会冒出一圈新接缝）。
- 星云 / 星空**仍用** `window`（问题 3 已决定保留星云观感），变色差 `ab` 跟着 `defl` 走，无需另动。

> ⚠️ 接手时这里有个**半成品**：`windowDisp` 已经算好并塞进 `LensSample`，但两条位移分支都没用它
> —— 等于没生效，而文档还写着「未动代码」。本步把它真正接上了（这也是为什么必须先写测试：
> 光看代码根本发现不了它没接）。

**取证（最关键的一条）**

新写的断言在**旧行为下**精确复现了重影环带：

```
半径 93px 处 alpha 已羽化到 0.973，位移却仍有 4.71px
```

（256² 视口、阴影半径 16px、fadeR = 8 rs = 128px；换算到 1080p 约在半径 390px 一带。）
这正是「半透明 + 还有偏移」的环带 —— `bugs/边缘bug.jpg` 里的重影就在这一圈。
修复后该处位移为 0。

**测试**（新增 `tests/LensFadeOrderingTests.cs`，4 项；全量 **594 通过 / 0 失败**）
- 新增验证入口 `LensFadeProbePS`：一次渲染同时读出
  `r = windowDisp` / `g = alpha 羽化系数` / `b = 位移幅度`
  —— 重影是**观感**，单看颜色分不出「半透明区有没有偏移」，必须两个数一起拿。
- [x] `NoDisplacement_WhereTheAlphaIsSemiTransparent`（主判据）：羽化区内位移必须 ≈ 0
- [x] `DisplacementEndsBeforeTheFeatheringStarts`（顺序判据）：位移归零**早于**羽化开始
- [x] `TheLensIsStillFullStrengthNearTheShadow`（反向保护）：阴影附近位移仍是满强度
      —— 防「为了去重影把透镜整个关掉」
- [x] `TheAlphaStillFadesOutAtTheViewportEdge`：羽化本身还在（否则屏幕四周会出现矩形硬边）

> **验证断言本身有效**：改回旧的 `* window` 后，前两条**立刻失败**（就是上面那条 93px 的消息），
> 说明它们不是空过。这种「先确认新断言在旧代码上会红」的做法以后继续保持。

**代价（要你实机看一眼）**：透镜的可见范围从约 8 rs 收到约 **5.7 rs**
（位移在 3.75 rs 内是满强度，3.75~5.67 rs 平滑归零）。这是方案 a 的预期代价 ——
重影没了，但远处那圈很弱的偏折也一起没了。如果你觉得「势力范围变小了」，
可以把 `0.45 / 0.68` 往外挪（只要保证 `< 0.70`，位移就一定先于羽化归零）。

## 问题 2 — 星空 / 星云变化速度太慢，需要可调速度

**你的反馈**：*「星空跟星云变化速度有点慢 需要可调速度」*

**现状**（`common.hlsl`）
- 星云：`p += Timing.y * (0.015, 0.006)`（平移）+ 明暗呼吸 `0.85 + 0.15·sin(t·0.25)`（周期约 25 秒）
- 星空：闪烁 `0.7 + 0.3·sin(Timing.y × (0.5~2.5) + …)`，以及随光标位置的漂移（问题 8 加的）

**要点**：这些系数都是**写死的常量**，没有任何设置项可调。

**方案草案（实现时细化）**
- 新增一个「氛围流速」参数（如 `AmbientFlowSpeed`，0~3，默认 1），
  乘在星云平移 / 呼吸与星空闪烁的时间项上 —— 一个滑块同时管两层，
  语义是「变化快慢」而不是「亮度」（亮度已有各自的 Gain）。
- 传参通道：`Timing` 或 `Extra` 还有保留分量可用，不必扩 cbuffer。
- 外观页放在「星空强度 / 星云强度」附近。

### ✅ 问题 2 已修（2026-09-26）：新增「氛围流速」滑块

**一个参数管两层**：`AmbientFlowSpeed`，0–3，默认 **1（= 原速）**，0 = 完全冻结。

| 层 | 链路 |
|---|---|
| 设置 | `SettingsModel.AmbientFlowSpeed` + `SettingsRanges.AmbientFlowSpeedMin/Max`，`Clamp()` 已接 |
| 传参 | `SceneConstants.Timing.z`（原本就是「保留」分量，**没扩 cbuffer**） |
| 着色器 | `common.hlsl` 新增 `AmbientTime() = Timing.y * Timing.z`；星云平移 / 呼吸、星空闪烁**全部走这一个入口** |
| UI | 外观页「渲染」区新增滑块 **氛围流速**（在星云色调下方），`SliderRow` 直连 Min/Max 常量 |

**三个刻意的选择**
1. **只乘时间项**，不乘位置项（`Extra.xy` 的视差）—— 否则「移动鼠标时图案跟着漂」
   会被改成「移动鼠标时图案乱跳」，那是另一个维度的事。
2. **一个入口** `AmbientTime()`，而不是星云与星空各乘一次 —— 以后要加第三层氛围时不会漏乘。
3. **不进预设**（与 `NebulaGain` 一致）：快慢是用户口味，不是外观；
   所以 `SettingsModel.ApplyAppearanceFrom` 的 15 个字段没动，预设相关测试零改动。

**一个容易踩的坑（已规避）**：老配置文件里没有 `AmbientFlowSpeed` 这一项。
`System.Text.Json` 遇到缺字段**不会调用 setter**，于是字段保持初始化值 `1.0`
—— 只要把默认值写在字段初始化器里就安全。若哪天改成「缺字段按 0 处理」，
老用户的氛围层会被静默冻结，这条要写进注释提醒。

**测试**（新增 `tests/AmbientFlowTests.cs`，6 项；全量 **602 通过 / 0 失败**）
- [x] `Default_IsTheOriginalSpeed`（默认 1）、`Clamp_KeepsItWithinZeroAndThree`
- [x] `Builder_PutsTheSpeedInTimingZ`（参数真的送到着色器，滑块不白摆）
- [x] `HigherSpeed_EvolvesFaster`：同样 6 秒真实时间里，2.5 倍速的变化量 > 原速 × 1.4
- [x] `ZeroSpeed_FreezesTheAmbient`：0 = 星空不闪、星云不漂
- [x] `SpeedDoesNotChangeTheOverallBrightness`（反向保护）：调的是**变化快慢**，不是亮度
- 顺带把 `AmbientFlowSpeed` 加进 `AppearanceBindingTests.SlidersCoverAllAdjustableV2Parameters`
      （漏了这条的话，滑块可以悄悄消失）

> **验证断言本身有效**：让 `AmbientTime()` 临时忽略倍率后，
> `HigherSpeed_EvolvesFaster` 与 `ZeroSpeed_FreezesTheAmbient` **立刻红**
> （实测「2.5 倍速 → 1.53 / 原速 → 1.53」，完全没区别），说明不是空过。

**未做**：没有给「星空」与「星云」拆成两个独立速度 —— 你要的是「一个可调」，
拆开会让外观页再多一个滑块。若以后发现两层想要不同的快慢，再加一个参数即可
（通道还有 `Extra.z` 空着）。

## 问题 3 — 星云的蓝色圈（范围很大），想去掉

**你的反馈**：*「黑洞开启星云后会出现一圈较蓝的圈围住他(范围很大) 看看能不能去掉这个蓝色」*

**初步定位**

两层因素叠出来的：

1. **配色**：`nebula()` 的暗端是写死的冷蓝 `float3(0.26, 0.44, 1.00)`，
   亮端才是 `NebulaTint`（预设可带）。所以云的**稀薄边缘**全是这个蓝。
2. **alpha 拉满**：`composite.hlsl` 的
   `ambientAlpha = max(ambientAlpha, nebulaEnabled * (Timing.w > 0.5 ? 1.0 : 0.0))`
   —— 这是 fixes-v2 问题 5 的修复（保证折射层取不到桌面时星云能顶上）。
   但全屏后它变成**与位置无关的常量**（P1.4 已记录），整屏 alpha = 1
   ⇒ 星云**整屏可见**，那圈冷蓝的稀薄边缘自然又大又明显。

**为什么问题 1 的修法不能顺手解决它**：问题 1 是「位移与 alpha 的时序错配」，
这个是「暗部配色 + alpha 恒满」—— 就算位移归零，蓝圈还在（它是星云自己的颜色）。

**候选修法（组合使用，实现时定）**
- **暗部透明**：`ambientAlpha` 不再恒满，改为**按星云亮度加权**
  （亮处不透明、暗处透出桌面）—— 但必须保住 fixes-v2 问题 5 的底线：
  折射层取不到桌面内容的那一圈仍然要被顶住（那里桌面本来就取不到，不存在「透出」问题，
  需要区分「取不到」与「星云很暗」两种情形，不能一刀切）。
- **暗部去蓝**：冷端往中性灰 / 暗部透明过渡，或者把暗端也交给 `NebulaTint` 的暗部版本（预设可带）。
- 或者最简单：给星云加一个「范围」参数，把云限制在黑洞附近（但这会回到「圈」的观感，可能不符合预期）。

**✅ 你的决定（2026-09-25）**：**「去掉蓝色，星云照常可见」** ——
只改暗部配色，不动 alpha 结构。风险最小，星云的观感保留。

**据此确定的修法**
- 把 `nebula()` 的暗端从写死的冷蓝 `float3(0.26, 0.44, 1.00)` 改成**不偏蓝**的过渡色
  （中性偏暗 / 或直接淡到透明），稀薄边缘就不会再泛蓝。
- 亮端仍由 `NebulaTint` 决定（预设可带，fixes-v2 问题 6 的成果保持不变）。
- **不动** `ambientAlpha` 那条常量项（`nebulaEnabled * (Timing.w>0.5?1:0)`）——
  它是 fixes-v2 问题 5 的底线（折射层取不到桌面时星云要顶住），动了会引出回归。

### ✅ 问题 3 已修（2026-09-26）

**改动**（`common.hlsl` 的 `nebula()`，只动暗端配色）

```hlsl
// 旧：暗端是写死的饱和冷蓝
float3 cool = float3(0.26, 0.44, 1.00);

// 新：亮端色调的**去饱和暗部版本** —— ① 按亮度压成灰 ② 掺回 25% 原色调 ③ 归一到旧亮度
float3 luma = float3(0.299, 0.587, 0.114);
float grayLevel = dot(warm, luma);
float3 gray = float3(grayLevel, grayLevel, grayLevel);
float3 desaturated = lerp(gray, warm, 0.25);
float3 cool = desaturated * (0.42 / max(dot(desaturated, luma), 1e-3));
```

三步各自的理由：
- **① 压成灰**是去蓝的本体：蓝是**饱和度**问题，不是亮度问题，所以先动饱和度而不是直接调暗；
- **② 掺回 25%** 让暖色预设的暗部仍带一点暖，不至于变成死灰（同时也保留了 fixes-v2 问题 6
  「预设自带星云色调」的成果 —— 暗端也跟着预设走了）；
- **③ 归一到 0.42**（旧冷蓝亮度约 0.45）：亮度基本不变、只去掉蓝 ——
  你要的是「去掉蓝色，**星云照常可见**」，把暗端调暗就等于把星云改没了，那是另一种回归。

**实测（隔离渲染：纯黑底 + 盘关 + 星场关，只看星云）**

| | 稀薄处平均色（R / G / B） | 蓝比红高 |
|---|---|---|
| 修前 | 8.9 / 12.1 / **25.1** | **+16.2** ← 那圈蓝 |
| 修后 | ≈ 11.4 / 11.6 / 12.0 | **+0.6** |

**测试**（`NebulaTests` 新增 2 项；全量 **596 通过 / 0 失败**）
- [x] `TheThinNebulaIsNotBlue`：取「暗但不为 0」的像素（正是 `cloud` 落在 0.12 亮度地板上的稀薄区，
      也就是全屏后变成一大圈的那片），断言 `B − R ≤ 8`
      —— 旧行为下实测 `R=8.9 / G=12.1 / B=25.1`，**会红**，不是空过
- [x] `TheThinNebulaIsStillVisible`：稀薄处平均亮度仍 > 4（去蓝不能把星云改没）
- 原有 12 项全过，其中 `ADarkDesktopStillShowsLight` / `HigherNebulaGain_IsBrighter` /
  `NebulaColor_ChangesTheGlowColor` 是「星云照常可见 + 预设色调仍生效」的现成保护

**未动**：`ambientAlpha` 常量项（fixes-v2 问题 5 的底线）、星云亮度地板 0.12、
亮端 `NebulaTint`、时间流动与呼吸（那些是 fixes-v2 问题 4 / 8 的成果）。
也就是说「整屏 alpha = 1」这个全屏带来的后果仍在（plan-v3 P1.4 有记录），本次没碰。

## 问题 4 — 透镜区域的变化速度跟不上画面其他部分

**你的反馈**：*「引力透镜透过的地方变化速度跟不上其他地方的（在滑动滚轮的时候能看到）肉眼看着很明显」*

**初步定位：这是抓屏链路的固有延迟，不是渲染慢**

```
画面其他部分：  DWM 直接合成             → 延迟 ≈ 0
透镜透过的部分：桌面上抓取 → 我们渲染 → 再合成
                 └ GDI CopyFromScreen 每次要付一次 DWM 同步等待（实测 ~17ms）
```

- 内容快速变化时（滚滚轮、视频、动画），透镜区显示的是**至少 17ms 前**抓到的那一帧，
  旁边没被透镜覆盖的区域却是实时的 —— 两者并排，肉眼就能看出「慢半拍」。
- 内容静止或变化慢时看不出来，这与你的观察（滚滚轮才明显）一致。

**为什么「搬后台线程」没能解决它**：后台线程解决的是「抓屏**阻塞**主循环
导致帧时间波动 → 抖动」，它**并没有**缩短抓屏本身的延迟 ——
那一帧从「抓取」到「显示」仍然要走完整条链路。
（实测 57 FPS、整帧 1.67ms，帧率完全没问题；滞后的只是**内容年龄**。）

**候选修法**

| 方案 | 做法 | 说明 |
|---|---|---|
| **a. 缩短链路** | 改用 **Windows.Graphics.Capture**（零拷贝 GPU 直传） | 参考实现正是这么做的。`plan-v3` P0 阶段已确认 `IsSupported=True`；但 C# 侧 COM 互操作当时卡在 `CreateForMonitor`（工厂 QI 返回 `E_NOINTERFACE`），需要重新攻关 |

### ✅ 根因（真）：**远场 / 近场交界圆**两侧算「天球方向」的两套算法不一致

`common.hlsl` 的 `nebula()`：

```hlsl
float2 sph = float2(atan2(d.x, -d.z), asin(clamp(d.y, -1.0, 1.0)));
float2 p   = sph * 2.2;                       // ← 2.2 格 / 弧度
...
n += amp * vnoiseWrapY(p * freq, 64.0);       // ← 只 wrap 了 **y**
```

- 一整圈是 `2π × 2.2 = 13.82` 格 —— **不是整数**。
- 跨过 `atan2` 的分支切口（`d.x = 0 且 d.z > 0`）时，`sph.x` 从 `+π` 跳到 `−π`，
  于是 `p.x` 一下子跳 **约 13.8 格** ⇒ 两侧的噪声格子完全无关
  ⇒ 切口两侧是**两片互不相干的云**，接缝处就是一条硬缝。
- 而 `vnoiseWrapY` **只 wrap 了 y**（仰角），切口偏偏在 **x（方位角）** 上 ⇒ 完全没被兜住。
- **为什么只在近场出现**：远场 `dirFar = normalize(float3(-pr * (2/b²), -1.0))` 的 z 恒为负
  ⇒ 永远跨不到切口；只有近场（积分出来的 `finalV`）在**偏折足够大**时才会指向 `+z`。
  ⇒ 缝必然落在**黑洞周围某条闭合曲线**上，**跟着黑洞动** —— 与你的观察完全一致。

> 📌 **这个坑本仓库出现过一次**：`vnoiseWrapY()` 的注释写的就是
> 「吸积盘条纹跨过 atan2 的分支切口时不会出现接缝」——
> 同一个 `sph` 参数化，盘那边当年做了 wrap（y 方向），星云这条路径的切口在 x 上，没兜住。

### ✅ 已修（2026-09-26，两处）

#### ① 交界圆的方向不一致（**你看到的那条缝**）—— `lens.hlsl`

```hlsl
// 远场：解析弱偏折反推方向
float3 dirFar = normalize(float3(-pr * (2.0 * binv * binv), -1.0));
// 近场：测地线积分终态
float3 dirNear = normalize(finalV);
```

位移（`defl`）当年已经校准到交界处连续（M1.5「交界圆无缝」说的就是这个），
但**方向**没管 —— 星云 / 星空是**按方向索引**的 ⇒ 那一圈上取到两片互不相干的值 ⇒ 硬缝。

修法：`b` 接近 `bmax` 时把方向平滑地让给解析式，交界处两侧就接上了：

```hlsl
float blend  = smoothstep(bmax * 0.75, bmax, b);
float3 dirSky = normalize(lerp(dirNear, FarSkyDirection(pr, b), blend));
```

只影响 `b ∈ [0.75·bmax, bmax]` 这一圈（远场解析式在那一带本来就够准），
光子环附近仍是积分终态，观感不变。顺带把解析式抽成 `FarSkyDirection()`，
